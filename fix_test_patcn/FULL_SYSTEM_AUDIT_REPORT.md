# Повний системний аудит та технічний аналіз 5 проблем

## 1. Позиціонування на Android, планшетах (Full HD) та браузері Waterfox

### 1.1. Першопричини збою на планшетах (1600x720 працює, а Full HD 1920x1080/1200 зникає):
1. **Штучне обмеження `isMobile = currentInnerW < 1024`:**
   * У `src/hooks/useVisualViewport.ts` (рядок 48) прописано:
     ```ts
     const isMobile = currentInnerW < 1024;
     ```
   * У рядку 73 того ж файлу віртуальна клавіатура розпізнається ТІЛЬКИ якщо `isMobile === true`:
     ```ts
     const isKeyboardOpen = isMobile && ((isInputFocused && heightShrinkDiff > 130) || ...);
     ```
   * На Full HD планшеті (наприклад, 1920x1200 в альбомі або 1200x1920 у портреті) `window.innerWidth >= 1024`. Тому `isMobile` обчислюється як `false`.
   * Як наслідок: `isKeyboardOpen` завжди залишається `false`, `--keyboard-offset` встановлюється в `0px`.
2. **Стилі TamedWidget:**
   * У `src/components/editor/TamedWidget.tsx` (рядок 208):
     ```ts
     isMobile: typeof window !== 'undefined' ? window.innerWidth < 1024 : false
     ```
   * У `src/lib/viewportLayout.ts` функція `getFloatingWidgetStyles` при `isMobile === false` повертає порожні стилі без розрахунку `top`/`bottom`.
   * Віджет залишається зафіксованим класом `fixed sm:absolute bottom-4`, опиняючись повністю під віртуальною клавіатурою.
3. **Розрахунок відступу каретки в редакторі:**
   * У `src/lib/viewportLayout.ts` функція `calculateEditorBottomReserved` перевіряє `if (isMobile)`. Якщо екран >= 1024px, вона ігнорує клавіатуру і резервує лише стандартні 76px, тому текст заїжджає під клавіатуру планшета.

### 1.2. Особливості браузера Waterfox / Firefox Android проти Google Chrome:
* **Підтримка мета-тега `interactive-widget=resizes-content`:**
  * Google Chrome 108+ нативно підтримує цей прапорець і зменшує `window.innerHeight` разом із `visualViewport`.
  * Рушій Gecko (Firefox/Waterfox Android) не завжди підтримує цей режим або підтримує його з накладанням (overlay).
  * Waterfox має плаваючий нижній адресний рядок, який ховається при скролі. Різниця між `window.innerHeight` та `window.visualViewport.height` має обчислюватися безумовно, базуючись на наявності сенсорного введення (`navigator.maxTouchPoints > 0`) та реальному зменшенні `visualViewport`, а не на фіксованій ширині 1024px.

## 2. Мобільний вигляд, зсуви хедера від модальних вікон та перенесення довгих заголовків

### 2.1. Чому виникаючі вікна та клавіатура рухають хедер:
1. **Зсув `window.scrollY` при фокусі інпутів всередині модальних вікон:**
   * Коли користувач тапає в поле введення в модальному вікні, браузер Android намагається прокрутити сторінку (`window.scrollTo`), щоб поле опинилося в центрі.
   * Оскільки кореневий контейнер має `height: 100dvh` або фіксовану висоту, прокручування вікна `window` зміщує `Header` вгору за межі видимої області.
2. **Розширення сторінки по ширині (горизонтальний скрол у портретному режимі):**
   * У `src/components/header/Header.tsx` випадне меню інструментів має клас `fixed top-14 left-2 right-2 sm:absolute sm:top-full ... sm:w-max max-w-[95vw]`.
   * Деякі внутрішні групи іконок без `flex-wrap` або з фіксованою шириною перевищують ширину екрана вузьких смартфонів (360px), через що хедер розширюється і зсувається вбік.

### 2.2. Режим читання та великі заголовки:
* У `src/components/docReader/DocReaderContent.tsx` рядок 118:
  ```tsx
  <h1 className="text-2xl sm:text-4xl font-bold tracking-tight mb-3 leading-tight">
  ```
  Немає класів `break-words`, `overflow-wrap: anywhere` чи `hyphens: auto`.
* Якщо заголовок містить довге нерозривне слово (наприклад, технічний термін, довге українське чи німецьке слово, посилання), він фізично виходить за межі екрана мобільного пристрою, розтягуючи всю сторінку в ширину.

## 3. Прозорість, важкі рендери (Tauri/Windows) та прив'язка кольорів тем

### 3.1. Різниця рендерингу на Windows (Tauri / WebView2):
* На Windows застосунок працює на рушії Edge WebView2. При використанні `backdrop-blur-*` та напівпрозорих фонів (наприклад `bg-slate-900/80`, `bg-slate-950/90`) без явної суцільної непрозорої підкладки компоновщик DWM Windows просвічує фонові вікна робочого столу або створює "скляний" артефакт.
* На Linux (WebKitGTK) та Android (Chromium) `backdrop-blur` часто або емулюється як суцільний колір, або взагалі ігнорується, тому там цієї прозорості не видно.

### 3.2. Аудит жорстких прив'язок до кольорів:
* У проєкті виявлено **32 випадки використання `backdrop-blur`**, **382 випадки жорстко прописаних `bg-slate-*`** та **666 випадків жорстких кольорів тексту**.
* `src/index.css` містить понад 80 рядків "милиць" виду `.theme-light .bg-slate-900 { background-color: var(--bg-sidebar) !important; }`.
* Якщо будь-який компонент використовує клас із модифікатором, якого немає в списку (наприклад `bg-slate-900/95`, `bg-slate-950/90`, `bg-black/60` у галереї `ImageItem.tsx` чи `AppModals.tsx`), у білій темі залишається чорна напівпрозора плашка з білими іконками.
* Неонова тема працює стабільно, оскільки вона побудована на глибоких темних відтінках (`bg-slate-950`), які гармоніюють із темними плашками.

## 4. Стрибки та смикання скролінгу в режимі читання

### 4.1. Першопричини:
1. **Знищення та перевстановлення всього DOM під час скролінгу:**
   * У `src/components/docReader/DocReaderContainer.tsx` подія `onScroll` викликає `handleScroll`.
   * `handleScroll` постійно оновлює `activeHeadingId`.
   * У `DocReaderContent.tsx` ефект `useEffect` слухає `[content, headings]`:
     ```tsx
     useEffect(() => {
       processContent(); // викликає marked.parse + DOMPurify.sanitize + setRenderedHtml
     }, [content, headings]);
     ```
   * Якщо передається новий масив `headings` або змінюється стан, компонент викликає `setRenderedHtml`, що повністю перезаписує `dangerouslySetInnerHTML`.
   * Знищення DOM під час руху пальця чи коліщатка збиває якір скролінгу браузера, через що сторінка "перескакує" абзаци або відкочується назад.
2. **Синхронний Layout Thrashing у `handleScroll`:**
   * На кожен піксель прокручування викликається `getBoundingClientRect()` для кожного заголовка `h1-h6` без троттлінгу чи `requestAnimationFrame`. Це викликає мікро-фрізи потоку рендерингу (jank).
3. **Відсутність резервованих розмірів у зображень (Cumulative Layout Shift):**
   * Картинки в Markdown вставляються без атрибутів `width`/`height` чи `aspect-ratio`. Під час скролінгу вони довантажуються асинхронно і раптово змінюють висоту контейнера на сотні пікселів.
4. **Конфлікт `position: fixed` на `body` із мобільним touch-скролом:**
   * `index.css` фіксує `body` з `position: fixed; touch-action: manipulation; overscroll-behavior: none;`. При швидкому інерційному скролі на Android тач-жест впирається в границю і скидає інерцію.

## 5. Звуковий супровід: технічні шуми, затримки на Android та архітектура Worker/Store

### 5.1. Чому Android відстає від клавіш і грає лише один монотонний звук:
* На віртуальних клавіатурах Android (Gboard, Samsung Keyboard) подія `keydown` приходить із кодом `keyCode: 229` та `e.key = "Unidentified"`.
* У `src/services/audio/useTypingSound.ts`:
  1. `handleKeyDown` отримує `Unidentified`, відтворює дефолтний монотонний звук і записує:
     ```ts
     lastPhysicalKeyDownTimeRef.current = performance.now();
     ```
  2. Через 5-15 мс надходить подія `beforeinput` із реальним символом у `e.data`.
  3. Але рядок 187 містить блокування:
     ```ts
     if (performance.now() - lastPhysicalKeyDownTimeRef.current < 90) return;
     ```
  4. Подія `beforeinput` з реальним символом **ігнорується та викидається**!
  5. У результаті програється ТІЛЬКИ "Unidentified" звук — один і той самий тон для всіх клавіш!

### 5.2. Причини технічних шумів, клацань та тріску:
1. **Розриви фази та планування в минулому часі:**
   * Виклик `setValueAtTime(0.0001, startTime)` при `startTime = ctx.currentTime`. Якщо потік JS був зайнятий рендером React на 2 мс, `startTime` опиняється в минулому відносно аудіо-рушія, що викликає різкий цифровий клік (step discontinuity).
2. **Повна відсутність обмеження поліфонії (Voice Limiting):**
   * При натисканні 10 клавіш поспіль створюється до 100+ аудіо-вузлів одночасно. Усі вони підсумовуються в компресорі та сатураторі (`WaveShaper`), викликаючи нелінійні спотворення та кліпінг.
3. **Витік та паузи збирача сміття (Garbage Collection):**
   * Кожен звук створює 8-14 вузлів C++ WebAudio та ставить `setTimeout` на 1.5-3 секунди для їхнього `.disconnect()`.
   * Масове створення та знищення об'єктів на головному потоці викликає GC-паузи, що призводить до спустошення аудіобуфера (buffer underrun — характерний тріск).

### 5.3. Чи потрібен Web Worker та Store:
* **Web Worker:** `AudioContext` у більшості мобільних браузерів прив'язаний до головного потоку вікна і не може бути створений у звичайному Web Worker (крім AudioWorklet для DSP).
* **Zustand Store + Voice Pool (Правильне рішення):**
  * Зараз аудіо керується хуком `useTypingSound` у React-компонентах. Потрібно винести стан у легкий **Zustand store** (`useAudioStore`) або прямий синглтон-диспатчер.
  * Реалізувати **Voice Pool** (пул із 6-8 фіксованих голосів) із плавним перехопленням голосу (voice stealing) та загасанням 5 мс. Це повністю прибере створення нових вузлів при кожному тапі, усуне збирання сміття та ліквідує шуми.
