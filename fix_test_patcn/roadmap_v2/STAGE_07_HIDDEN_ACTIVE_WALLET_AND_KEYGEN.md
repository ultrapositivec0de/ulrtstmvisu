# Етап 7: Прихований гаманець Active-операцій з поакаунтним шифруванням та локальним Keygen

**Рейтинг**:
- **Важливість**: Висока
- **Складність**: Висока
- **Ресурсна вартість**: Висока
- **Залежності**: Етапи 1, 6

---

## Мета етапу
Створити окремо прихований модуль фінансових та акаунт-операцій Steem на базі Active Key із суворою криптографічною ізоляцією від щоденного Posting-сейфа: кожен фінансовий акаунт шифрується окремо власним індивідуальним PIN-кодом/паролем. Додати повний набір фінансових функцій (перекази, SP, DEX, випуск ACT та створення акаунтів із локальною генерацією ключів).

---

## Критичні вимоги безпеки

1. **Повністю окреме сховище шифрування (`steem_private_active_vault_v1`)**:
   - Не використовує ключі, сіль або майстер-ключ стандартного `SecurityService` (`steem_vault_*`).
2. **Незалежний PIN-код / пароль для кожного фінансового акаунту**:
   - Для кожного доданого акаунту зберігається окремий запис `{ username, salt, iv, ciphertext, kdfIterations }` у IndexedDB.
   - При додаванні другого чи третього фінансового акаунту користувач задає **окремий PIN-код/пароль саме для цього акаунту**; розблокування одного акаунту в оперативній пам’яті не відкриває доступ до жодного іншого Active-ключа.
3. **Коротке автоблокування та мінімальний час життя ключа в RAM**:
   - Дешифрований `PrivateKey` тримається в пам’яті виключно на час сесії активного вікна гаманця з автоматичним обнуленням за таймером бездіяльності (напр. 3 хв) або при закритті модуля.
4. **Обов’язковий дисклеймер безпеки**:
   - При першому відкритті та додаванні ключа демонструється явне попередження, що це приватний інструмент, який працює локально на пристрої користувача, без серверної опіки та без зовнішніх фінансових гарантій з боку авторів редактора.
5. **Прихована точка входу**:
   - Модуль не виноситься на головну панель редактора; доступ відкривається через приховану опцію у налаштуваннях/безпеці (або спеціальний перемикач режиму приватних операцій).

## Покроковий план дій

- [ ] **Крок 7.1 — Ізольований сервіс шифрування (`src/services/security/activeVaultService.ts`)**:
  - Реалізація Web Crypto `PBKDF2 (600 000 ітерацій, SHA-256)` + `AES-GCM 256` окремо для кожного запису `ActiveAccountRecord`.
  - Методи: `addActiveAccount(username, activeWif, accountPin)`, `unlockActiveAccount(username, accountPin)`, `lockActiveAccount(username)`, `lockAllActiveAccounts()`, `removeActiveAccount(username)`.
  - Валідація перед збереженням: перевірка через `condenser_api.get_accounts`, що введений WIF справді відповідає публічному `active` ключу вказаного `@username` (захист від помилкового введення Owner чи Posting ключа замість Active).
- [ ] **Крок 7.2 — Інтерфейс прихованого входу та дисклеймер (`src/components/wallet/HiddenWalletGate.tsx`)**:
  - Вікно підтвердження ризиків і дисклеймера (збереження прапорця ознайомлення).
  - Список збережених фінансових акаунтів із окремим індикатором блокування (`Locked` / `Unlocked`) і запитом індивідуального PIN для кожного акаунту при виборі або перед підписом транзакції.
- [ ] **Крок 7.3 — Перекази, Power Up / Power Down та Делегування (`src/components/wallet/ops/`)**:
  - **Переказ (`transfer`)**: вибір валюти (`STEEM` / `SBD`), отримувач з автоперевіркою існування акаунту на блокчейні, сума, поле `memo`, перевірка доступного балансу.
  - **Power Up (`transfer_to_vesting`)**: переведення ліквідного `STEEM` у `Steem Power` (собі або іншому акаунту).
  - **Power Down (`withdraw_vesting`)**: запуск виведення `SP` (конвертація суми SP у `VESTS` за поточним курсом `total_vesting_fund_steem / total_vesting_shares`) та кнопка скасування активного Power Down (`0.000000 VESTS`).
  - **Делегування (`delegate_vesting_shares`)**: видача делегації іншому акаунту, перегляд списку поточних вихідних делегацій (`get_vesting_delegations`) і зменшення/зняття делегації в один клік.
- [ ] **Крок 7.4 — Внутрішня біржа Steem DEX (`src/components/wallet/dex/SteemDexPanel.tsx`)**:
  - Читання стакану ордерів (`get_order_book`), курсу (`get_ticker`) та відкритих ордерів користувача (`get_open_orders`).
  - Створення лімітного ордера (`limit_order_create`: купівля/продаж `STEEM <-> SBD` з параметром `fill_or_kill` та часом життя ордера) і скасування активного ордера (`limit_order_cancel`).
- [ ] **Крок 7.5 — Токени створення акаунтів (ACT) та створення нового Steem-акаунту (`src/components/wallet/accounts/`)**:
  - Відображення поточного балансу `pending_claimed_accounts` акаунту.
  - Випуск токена без витрати STEEM через RC (`claim_account` з перевіркою наявного RC).
  - Форма створення нового акаунту двома шляхами: через наявний ACT (`create_claimed_account`) або за стандартну комісію STEEM (`account_create`), з перевіркою доступності нового імені `lookup_accounts`.
- [ ] **Крок 7.6 — Опціональний локальний генератор ключів нового акаунту (`src/services/steem/accountKeygenService.ts`)**:
  - Окремий опціональний режим у формі створення акаунту: **«Згенерувати ключі локально»** або **«Вставити готові публічні ключі вручну»**.
  - При виборі локальної генерації: генерується стійка криптографічна фраза/seed через `crypto.getRandomValues` і виводяться 4 окремі пари ключів (`Owner`, `Active`, `Posting`, `Memo`) за допомогою `@blazeapps/dsteem`.
  - Обов’язковий крок збереження резервної копії (завантаження `.txt`/`.json` файлу або копіювання + чекбокс підтвердження користувача, що приватні ключі збережено надійно).
  - У саму блокчейн-транзакцію передаються **виключно публічні ключі (`STM...`)**; приватні ключі нового акаунту нікуди не відправляються.

## Критерії приймання
- Додавання двох різних фінансових акаунтів вимагає окремого PIN для кожного; пароль першого акаунту не розшифровує ключ другого.
- Транзакції переказу, Power Up/Down, делегування, ордерів DEX, `claim_account` та `create_claimed_account` формують валідні структури операцій Steem і проходять перевірку типів та тест-підпис.
- При локальній генерації ключів у payload транзакції потрапляють тільки публічні `STM...` ключі.
- Posting-сховище та Active-сховище фізично розділені в IndexedDB і не перетинаються.
